# 两个人的小饭桌 · 产品设计

整合版「我们的时光」的最新原型决定见 [prototype-decisions.md](prototype-decisions.md)；下文部分四 Tab 与粉色小饭桌描述记录的是早期版本。

## 产品定位

“两个人的小饭桌”是仅供一对伴侣使用的私人电子菜单、点菜工具和吃饭记录。它只解决一件日常小事：轻松告诉对方今天想吃什么。产品不包含价格、支付、配送、库存或营销能力。

## 核心体验与原则

- 温馨但克制：奶油粉、白色、留白和自然文案，不做商业商城视觉。
- 两人协作：创建或加入同一个饭桌后，共享菜单和订单，收藏仍属于个人。
- 点菜优先：菜品信息服务于“想吃”，热量只做温和的家庭估算。
- 主流程可靠：外部通知和图片服务未配置时，登录、菜单和订单仍可独立工作。

## 用户流程

1. 首次打开使用 `wx.login` 登录，自定义昵称。
2. 创建“小饭桌”获得邀请码，或输入伴侣的邀请码加入；同一饭桌最多两人。
3. 在首页接受随机推荐，或在菜单按分类、关键词、标签找菜。
4. 收藏菜品或加入“今天的小菜单”，调整数量、餐次、日期和留言。
5. 同一饭桌、同一餐次和日期的未上菜菜单合并更新。首次提交后对方收到站内提醒，并在对方有可用订阅机会时收到微信提醒。
6. 做好后点击“上菜啦”，可选上传成品照片；上菜即完成这顿饭。
7. 已上菜订单进入“吃过”，可以一键“再来一顿”。

## 页面结构

底部四个 Tab：

- 今天：自定义欢迎文案、整张图片式随机推荐卡、双胶囊按钮、轮播指示和底部小提醒。推荐卡用真实菜品图片与文案；没有上传图片时显示统一占位，不伪造食物照片。
- 菜单：顶部大标题与按需展开的搜索，左侧纯文字纵向分类及已选数量，右侧方形图片菜品列表，底部固定“已选菜品”栏。底栏采用紧凑的珊瑚粉查看入口；展开层展示缩略图、菜名、估算热量、数量加减、单项删除、清空与提交。收藏入口保留在菜品详情。
- 吃过：默认直接显示按日期分组的饭饭记录，照片、餐次、状态、菜名和真实留言/评论在同一卡片中；更多菜单保留再次点菜与二次确认删除。若存在未上菜订单，页首显示精简入口。
- 我们：暖色生活场景背景、双头像、饭桌名、真实累计餐次、本月餐次与个人收藏数；收藏数直接进入个人收藏。下方只保留设置、消息提醒、我们的小记录和关于四个入口，避免重复导航。

四个主页面统一采用暖白底色、大留白和简洁卡片；粉色仅强调主要操作、选中状态与少量情感细节。入口图标使用项目内的线性 PNG 资源（保留 SVG 源稿），无图菜品使用统一的暖米色餐盘线稿占位，避免系统 Emoji 造成色调不一致。统计只展示后端真实数据，不使用原型图中的示意数值或虚构头像。订单当前以“已上菜（ready）”作为成功记录，饭桌餐次、菜品吃过次数和推荐近期惩罚均将 `ready` 及兼容旧数据的 `completed` 视为已吃过。

非 Tab 页面：绑定饭桌、菜品详情、今天的小菜单、订单详情、我的收藏、菜单管理、菜品编辑、分类管理、小饭桌设置和饭桌成员。小饭桌设置按“我的资料、我们的小饭桌、首页展示、日常管理、其他操作”分组；成员与邀请码集中在独立页面，退出及永久删除默认折叠。

## 数据结构

- `users`：微信 OpenID、昵称、头像、饭桌归属和未读数。
- `couples`：饭桌名称、稳定 UUID、一次性邀请码、到期时间、创建人、纪念日和首页主副标题。
- `couple_members`：用户与饭桌的保留关联、加入/退出时间；用户可在仍保留的饭桌间切换。
- `starter_categories` / `starter_dishes`：保留的示例菜单模板，不混入真实业务表；新饭桌默认不自动初始化这些模板。
- `categories` / `dishes`：按饭桌隔离的真实可编辑菜单，`couple_id` 强制非空。
- `dishes`：菜品、分类、图片、估算热量、时长、难度、辣度、标签和软下架。
- `favorites`：用户与菜品的个人收藏关系。
- `orders`：餐次、日期、留言、状态、目标用户、总估算热量和各阶段时间。
- `order_items`：包含菜名、图片、热量等不可变快照，保护历史记录。
- `notifications`：小程序内提醒、关联订单、已读时间。
- `meal_reviews`：保存已上菜记录的评论和饭后照片。

完整字段与索引见 `database/schema.sql`。

## API 结构

统一响应 `{ code, message, data }`，身份由 Bearer JWT 得出，业务查询必须带当前用户的 `couple_id`：

- `/api/auth`：微信登录、当前用户、资料更新。
- `/api/couples`：创建、加入、已关联饭桌列表、切换、查看、更新、刷新邀请码、退出和永久删除饭桌。
- `/api/categories`：饭桌分类列表、新增、编辑与安全下架。
- `/api/dishes`：检索、详情、增改、软下架、收藏。
- `/api/recommendations/today`：带收藏与近期食用权重的推荐。
- `/api/orders`：创建、列表、详情、上菜（可带照片）、评论、删除历史和再次点菜。
- `/api/notifications`：站内消息、已读、订阅配置与测试发送。
- `/api/uploads/cos-credential`：验证文件后签发 COS 临时凭证。

## 第一版功能

- 微信登录与自定义昵称。
- 两人饭桌创建/邀请码加入与数据隔离。
- 左侧分类点单布局、搜索、详情、热量、收藏和不可手改的历史点单次数。
- 今天的小菜单与本地持久化。
- 订单创建、“提交 → 上菜”状态流转、历史删除和再次点菜。
- 首页规则推荐与饭桌真实统计。
- 饭桌私有菜单首次由示例模板复制，全部菜品和分类均可新增、编辑、排序与软下架。
- 小饭桌名称、纪念日、首页文案、本人称呼与头像、成员查看、邀请码更新和退出管理。成员资料遵循本人可编辑、伴侣只读的边界；未上传头像时显示昵称首字。
- COS 安全直传、微信一次性订阅消息及站内消息兜底。
- Loading、空状态、错误重试、Toast 和统一占位图。

## 可能的后续方向

饭饭日历、数据导出和更细致的解绑/交接策略尚未纳入当前流程。现有“吃过”已支持评论和成品照片；文档中的后续方向不代表已实现功能。

## 2026-11 菜单与消息调整

- 图片已恢复原有系统裁剪、压缩和展示方式，不保留自定义裁剪页。
- 在架菜品只有“下架”；已下架后出现“重新上架”和“删除”。删除仅标记 `enabled=0, deleted_at=NOW()` 并从管理列表隐藏，数据库记录、图片与历史订单快照保留。原分类不可用时，先编辑选择可用分类再上架。
- 订单详情成功显示后，客户端将本次取得的本人未读通知编号提交给已读接口。本人和伴侣分别保存阅读状态；头像绿色对勾表示小程序内已读，不能替对方设置。全部已读仅作用于本人当前饭桌。消息页可见时每 5 秒自动刷新阅读状态，离开页面停止，返回时立即重新获取；这是短暂延迟同步，不是瞬时推送，不依赖 Redis 或消息队列。
- 新消息通过同一次事件编号关联双方收件记录。旧消息无法可靠配对，另一成员显示“无阅读记录”，不回填猜测结果。微信订阅消息没有已读回执。
